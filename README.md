# RG BC Checker add-on

Separate ServiceM8 Web Service Hosted Add-on for an Auckland-first, staff-managed BC watch list. Verify the deployed version and live ServiceM8 behaviour separately from this checkout.

## First-version behaviour

- Add up to 50 ServiceM8 job numbers at a time, separated by commas. Spaces around each number are ignored; pasted line-separated lists also work. The form includes an example; CSV and XLSX uploads are not supported. A signed-in ServiceM8 staff member adds and reviews jobs. Jobs missing a client name or address are skipped, and the add notification identifies each skipped job and its missing details.
- On the first check, record all consent events already present at the exact matched address as a **baseline**. Do not raise a new-candidate flag for those events.
- On later checks, identify consents by number (or a fallback event fingerprint when no number exists). A new event is marked **Needs review** once. An existing baseline application also moves to review when its status first appears as issued, approved, or granted.
- **Wrong BC** remembers the dismissal for that Job and consent number. Further observations of that number do not reopen it. **Right BC — stop checking** retains the decision and stops monitoring the Job. Staff may also stop a Job without confirming a BC.
- Re-adding a stopped Job starts a fresh baseline and clears that Job's old candidates. An already active Job is left unchanged.
- Address matching must be unique. An uncertain address or changed ServiceM8 Job address produces a visible check error; it does not attach another property's events.
- Each monitored Job appears as one row in a table with Job number, client, address, last checked, status, Check now, and Stop monitoring columns. Search matches three or more characters in the job number, address, or client name across all monitored jobs. Consent candidates and their review controls appear below the table without an accordion. Pagination and page size sit below the list.
- **Check now** runs an immediate address check. After a successful check, it updates the Job's Note field with `NO BC - [Date Checked]` or `BC - [BC number] - [Date Checked]` using the most recent classified building consent dated within three years, and creates one Job Diary entry with the check summary and the triggering staff member's name. The Diary POST uses the signed staff UUID for ServiceM8 impersonation. ServiceM8 controls the Diary header/byline, so verify its displayed attribution in a live account; the note content always states who triggered the check. It preserves other Note field text and replaces the earlier BC Check block or concise status. It does not confirm a candidate as the right BC. If a ServiceM8 write fails, the result is shown in BC Checker; do not repeat the button just to retry a partial write, because another Diary post may create another item.
- No email is sent. Scheduled checks continue to update BC Checker only; they do not create Job Notes or Diary items.
- The Add-ons menu renders BC Checker directly in ServiceM8's add-on canvas. The signed staff session travels in the add-on's forms, including pagination and review actions; it does not require a separate browser tab or a third-party cookie.
- Recent checker activity is a collapsed section visible only to active ServiceM8 staff with an Admin, Administrator, Developer, or Business Owner security role, the confirmed Royal Glass developer login, or additional staff UUIDs explicitly listed in `AUDIT_VIEWER_STAFF_UUIDS`. ServiceM8 custom role names do not reliably identify admin or developer access, so identify additional custom-role developers by their signed staff UUID rather than granting every member of a custom role access. It shows the latest 50 account events: job additions and attempts, Stop monitoring, Check now, scheduled checks, and Wrong BC / Right BC / Reopen decisions. Staff names are resolved from ServiceM8 for older rows when needed; an unavailable name displays as “Staff member”. Scheduled checks are attributed to BC Checker scheduler. Events already completed before this audit table is deployed are not backfilled.

The Homes timeline labels these as consent events. The add-on presents them as **candidates**, and staff confirm whether one is the right building consent for the ServiceM8 Job. A matching address alone does not establish that conclusion.

## Setup

### Vercel

Select **Node** as the framework preset and **Node.js 24.x** as the runtime. Keep the project root at this folder. Vercel detects the root `server.ts` as the Node server entry point; locally, `npm start` uses the same entry point. Leave the Build Command and Output Directory overrides off, as shown in the Vercel project settings.

Set the variables in `.env.example` in Vercel Project Settings for the environment being deployed. The local `.env` is ignored by Git and is not uploaded by importing the project. `APP_BASE_URL` must be the final HTTPS deployment URL and must agree with the ServiceM8 add-on registration. The database and app base URL alone are insufficient to start the server: the ServiceM8 credentials, allowed account UUID, and three secrets are also required.

No Vercel Cron Job is configured yet. Enabling it would start live Homes checks; add and verify the scheduler after OAuth, database migration, and a manual baseline check have been tested. Vercel Cron invokes a GET endpoint on a UTC schedule, while the current `/cron/check` endpoint expects an authenticated POST, so the scheduler route must be adapted before using Vercel Cron.

1. Run on Node.js 24 or newer with PostgreSQL. `npm install` and `npm run db:migrate` apply the add-on's own schema, including `checker_audit_events`, to a dedicated database. Apply this schema to the intended database before deploying code that reads the activity panel. The npm scripts load a local `.env` when present; Vercel supplies the variables through Project Settings.
2. Configure the names in `.env.example` as host secrets. Generate a random 32-byte base64 `TOKEN_ENCRYPTION_KEY`; use independent random 32-character-or-longer values for `SESSION_SECRET` and `CRON_SECRET`. The ServiceM8 App ID/Secret and database must be separate from Office Assistant and Company Check.
3. Register a separate Web Service Hosted Add-on. The source manifest is `public/manifest.json`, served at `${APP_BASE_URL}/manifest.json`; its PNG icon is `public/icon.png`. Use `${APP_BASE_URL}/events` as event callback, `${APP_BASE_URL}/oauth/start` as activation URL, and `${APP_BASE_URL}/oauth/callback` as OAuth return URL. Grant `vendor read_jobs read_customers read_staff read_security_roles manage_jobs publish_diary_items`. Existing OAuth connections must be reauthorised for `read_staff` and `read_security_roles` before staff names and activity access can be resolved. After applying the schema and reauthorising, run `npm run db:backfill-clients` against the intended database to fill client names for already monitored jobs. Jobs without a linked client remain blank.
4. Start with `npm start`. Configure a trusted scheduler to POST `${APP_BASE_URL}/cron/check` every **Monday at 9:00 am Pacific/Auckland**, with header `Authorization: Bearer <CRON_SECRET>`. The database due date selects each Job every second Monday after its first check. Each invocation processes at most ten due Jobs; if the list grows, call the endpoint repeatedly with suitable spacing or raise the bounded batch size after measuring run time.
5. Verify that one signed staff launch remains inside the ServiceM8 canvas, including add, pagination, manual check, wrong/right BC and stop controls. Then verify a known Job with existing historical consents, a Job with no candidates, and a newly appearing candidate before enabling regular checks. Keep the existing Address Check add-on's account-wide Homes rate budget in mind; scheduled batches use a 15-second gap, while manual checks and another add-on do not share that pacing.

The user stated that Royal Glass has written permission from Homes.co.nz covering scheduled commercial lookups. Retain that permission and its scope with the deployment record; the project does not include it.

## Local verification

Run `npm test` for matching and candidate state rules. `node --check src/*.mjs` can be run on each file for syntax. Live ServiceM8 OAuth, embedded signed menu launch and navigation, Homes data shape, scheduler timing, and database behaviour require staging verification with separate credentials and representative Jobs. No migration or outbound call was made in this local build.
